## 1. Executive Summary

An independent end-to-end code audit and targeted `NFT-05` remediation + local automated verification suite (`59/59` assertions passing after final edits) was completed for `nft-checkout-payment-gateway`.

**Overall Security Posture:** **CONDITIONALLY PRODUCTION-READY WITH ONE REMAINING BACKEND-DEPENDENT BLOCKER ON `POST /payment-api/voucher/send` (`NFT-05`)**.

- Critical vulnerabilities (`NFT-01` return URL order completion bypass, `NFT-02` insecure webhook authentication fallbacks, `NFT-03` missing server-side payment verification, `NFT-06` duplicate payments/TOCTOU races, `NFT-07` paid-order downgrade, `NFT-08` missing replay/merchant binding, `NFT-09` unintended cancellation hook behavior, `NFT-14` spoofable rate-limit headers) are **verified remediated** in the plugin source code and validated against automated tests.
- **Synchronous API Call & Safety Fixes (`NFT-15` & `NFT-16`):**
  1. Page-load hooks in [`includes/class-nft-checkout-payment-gateway-loader.php`](includes/class-nft-checkout-payment-gateway-loader.php) (`nft_checkout_admin_orders_screen_sync`, `nft_checkout_admin_order_sync_on_view`, and `nft_checkout_customer_order_sync`) were updated to queue non-blocking background sync via `nft_checkout_schedule_async_order_sync()`, and `sync_pending_orders()` now defaults `$allow_voucher_lookup` to `false` so unclicked customer voucher links are never redeemed automatically on cron/page loads (retaining explicit synchronous `'force'` lookup only when an admin triggers the manual **Check NFT Checkout payment status** order action).
  2. Context guards in [`includes/class-nft-checkout-payment-gateway.php`](includes/class-nft-checkout-payment-gateway.php#L2060-L2110) were tightened so `nft_checkout_hide_custom_payment_gateway_conditionally()` and `nft_checkout_enqueue_styles_and_scripts()` exclude `is_wc_endpoint_url('order-received')`, `is_admin()` AJAX calls, and non-Store-API `REST_REQUEST` endpoints.
  3. Added a defensive `WC_Order` and `isset($line_items[0]['name'])` guard in `nft_checkout_add_custom_label_to_order_row()` ([`includes/class-nft-checkout-payment-gateway.php`](includes/class-nft-checkout-payment-gateway.php#L1999-L2008)) and removed an unused `$safe_table_name` variable in [`includes/nft-checkout-payment-gateway-utils.php`](includes/nft-checkout-payment-gateway-utils.php#L260).
- **`NFT-05` Account Synchronization Resolved via Existing Backend Support + Remaining Blocker Documented:**
  1. **Resolved (`handle_cron_event` / manual sync):** Re-inspection of `rt-app-payment-backend` revealed that `POST /payment-api/check-merchant-status` already accepts `Authorization: Bearer <public_key>` and `x-api-secret: <secret_key>` HTTP headers with zero secrets in the request body (`{"is_sandbox": 0|1}`). [`NFT_CHECKOUT_PAYMENT_GATEWAY_Loader::handle_cron_event()`](includes/class-nft-checkout-payment-gateway-loader.php#L314-L466) was migrated off `POST /payment-api/sync-account-status` (which forced plaintext `secret_key` inside the JSON body) onto `POST /payment-api/check-merchant-status` via `check_account_key_pair_status()`. Unused legacy secret properties (`$public_key`, `$secret_key`, `$sandbox_public_key`, `$sandbox_secret_key`) were also removed from [`includes/class-nft-checkout-payment-gateway.php`](includes/class-nft-checkout-payment-gateway.php#L13-L73).
  2. **Remaining `BLOCKED – Backend Dependency` (`/voucher/send`):** Re-verification across all backend routers, middleware, and schemas confirmed that `POST /payment-api/voucher/send` (`send_voucher` in `app/modules/wordpress_api/router.py:81-87`, `VoucherSendRequest` in `schemas/voucher.py:34`, `VoucherService.send` in `vouchers.py:254`) strictly requires `api_secret` inside the JSON request body and does not read `x-api-secret` or HMAC headers; no alternative header-only voucher creation route exists (`POST /request-payment` also requires body `api_secret` and does not email vouchers, and `POST /place-order` is disabled with `401`). Therefore, overall **`NFT-05` remains `PARTIALLY FIXED / BLOCKED ON /voucher/send (Backend Dependency)`**.

## 3. Detailed `NFT-05` Backend Investigation Results (`rt-app-payment-backend`, Read-Only)

### 3.1 Existing Secure Authentication Functionality Identified in Backend
1. **`POST /payment-api/check-merchant-status`** (`app/modules/wordpress_api/router.py:172-181`, `service.py:1159-1206`, `tests/test_wordpress_api_db.py:1039-1052`):
   - Accepts `(session, payload: PluginPayload, api_key: BearerToken, x_api_secret: ApiSecretHeader = None)`.
   - Evaluates `secret_key = payload.get("api_secret_key") or payload.get("secret_key") or header_secret`.
   - Authenticates strictly against `user_credentials` for the named mode (`sandbox` when `is_sandbox=1`, `live` when `is_sandbox=0`), verifies merchant existence and application scope (`APPLICATION_ID`), checks merchant active vs inactive/blocked status (`200` active, `403` inactive, `401` missing/invalid key/secret/mode), and skips card floor checks when `amount` is omitted (`card_minimum_refusal(..., None)` returns `None`).
   - **Supports headers-only secret transport (`Authorization: Bearer <public_key>` + `x-api-secret: <secret_key>`) with `{"is_sandbox": 0|1}` in the JSON body — zero plaintext secrets in body or URL.**
2. **`POST /payment-api/dailylimit`**, **`POST /payment-api/update-txn-status`**, **`POST /payment-api/cancel-order-link`** (`router.py:107-160`):
   - Already read `x_api_secret: ApiSecretHeader = None`; the plugin already transmits secrets strictly via headers on all three routes.
3. **Other Backend Auth Patterns Checked & Confirmed Inapplicable to WordPress Merchant APIs:**
   - `SIGNED_ROUTES` (`app/middleware/api_security.py:74-97`) and `authenticate_service_request` (`app/core/service_auth.py:24-84`): internal Banking-to-Payment and payment-provider webhooks using platform/service signing keys, not WordPress merchant credentials.
   - `require_merchant_api_key` (`app/modules/wordpress_api/dependencies.py:96-108`): intentionally unported fail-closed stub (`401` on `/place-order`, `/fetch-customer-details`, `/update-customer-details`, `/orders/{pay_id}/status`).

### 3.2 Plugin Changes Applied for `NFT-05`
- **File changed:** [`includes/class-nft-checkout-payment-gateway-loader.php`](includes/class-nft-checkout-payment-gateway-loader.php#L305-L466)

### 3.3 Exact Remaining Backend Blocker (`BLOCKED – Backend Dependency`)
- **`POST /payment-api/voucher/send` (`api_secret` in JSON request body):**
  - **Plugin location:** [`includes/class-nft-checkout-payment-gateway.php`](includes/class-nft-checkout-payment-gateway.php#L1906) (`nft_checkout_prepare_payment_data()`) and lines `1396–1408`.
  - **Backend repository verification (`develop` @ `f8bf16ed`):** `send_voucher` (`app/modules/wordpress_api/router.py:81-87`) only extracts `payload: PluginPayload` and `api_key: BearerToken` (never `x_api_secret: ApiSecretHeader`). `VoucherSendRequest` (`app/modules/wordpress_api/schemas/voucher.py:34`) strictly requires `api_secret: str = Field(min_length=1)`, rejecting omission with HTTP `422`. `VoucherService.send()` (`app/modules/wordpress_api/vouchers.py:233-257`) authenticates exclusively against `request.api_secret`. `POST /payment-api/request-payment` (`schemas/payment_schemas.py:335`) has the identical `api_secret` body requirement and does not create/email vouchers.
  - **Live Dev deployment contract probe (`2026-11-10T16:00+05:30`):** A non-mutating `POST https://dev.rt.app/payment-api/voucher/send` carrying `Authorization: Bearer <probe>` + `x-api-secret: <probe>` HTTP headers without `api_secret` in the JSON body returned **`HTTP 422`**: `{"message":"Please check your details.","status":"error","code":422,"errors":{"api_secret":["Field required"]}}`, confirming the backend `x-api-secret` header update is **not yet deployed**.
  - **Status:** Removing `api_secret` from the `/voucher/send` JSON body before backend deployment would break voucher creation and checkout. The plugin continues transmitting `Authorization: Bearer` + `x-api-secret` headers alongside body `api_secret` over HTTPS so it is ready once deployed, and `NFT-05` remains **`PARTIALLY FIXED – /voucher/send BLOCKED (Backend Dependency)`** (cannot be marked `VERIFIED FIXED` until the backend update is deployed and confirmed).
